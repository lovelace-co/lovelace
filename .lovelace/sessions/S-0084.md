## Approach

Delegated to a programmer subagent with a diagnose-first brief: the Board render path looked uniform across columns and the existing insertion-line tests pass vacuously in jsdom, so the brief demanded a layout-faithful test harness (stubbed card rects, long scrolled column, repeated dragover events) to convict a mechanism before any fix, with an explicit ban on speculative rewrites.

## What happened

The two leading hypotheses (layout-feedback oscillation from the in-flow line, and the computed index landing below the fold) were exonerated by passing diagnostic tests. The convicted mechanism was the column's onDragLeave handler: its relatedTarget containment check clears the insertion line whenever the browser fails to report the sibling card on a card-to-card crossing, a known WebKit unreliability. Short columns rarely cross a card boundary mid-drag, so the defect only reads in the long Done column. Fix in apps/desktop/src/views/Board.tsx replaces the relatedTarget check with document.elementFromPoint, keeping the line while the pointer is inside the column and still clearing it on a true exit. Five regression tests added in apps/desktop/test/boardDropLine.spec.tsx with a red-first proof (the convicting test fails against the old check). Along the way the agent found why the existing tests were vacuous: this jsdom has no DragEvent, so fireEvent.dragOver silently drops clientY; the new tests dispatch MouseEvent('dragover') instead. Orchestrator audited the diff, attacked boundaries (null elementFromPoint, cross-column drags, pointer over the dragged card) and re-ran pnpm test (380 passing) and pnpm build.
