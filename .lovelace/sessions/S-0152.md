## Approach

Retest-first per the ticket: verify the five suspected mechanisms against the current code, reproduce what a harness can reproduce (multi-process stress scripts against a demo-project copy for torn presence reads, lost updates and index drop-outs; a deterministic core-call demonstration for the singleton presence leak), then delegate fixes to the programmer subagent in two rounds (core plus mcp, then the desktop store), audit each diff, and gate the high-stakes core work with a fresh-context adversarial verifier.

## What happened

All five mechanisms confirmed. Reproduction numbers before the fix: 3,553 empty presence reads and a started_at reset under concurrent beats; 885 torn index reads plus 35 polls with a ticket missing from a well-formed index; 1 lost status move in 30 trials; the singleton active_ticket leaking into an unrelated session's presence entry. Fixes: writeFileAtomic (temp plus rename, mode-preserving) across every concurrently read write in core and the host's document writes; withMutateLock (mkdir-as-mutex under state/mutate.lock with owner token, atomic rename steal after 30 s, 5 s timeout) around every load-modify-write-reindex span including setColumnOrder; beatPresence and presence-start no longer read the singleton (per-session marker, else the entry's previous ticket, else null); the desktop store defers watcher events during its own mutation windows through a depth-counted change gate and replays them as one toast-less reload. The verifier refuted the first-round lock steal path (non-atomic, double-hold constructed) and release (raw ENOENT after a steal), and caught the replay raising the files-changed toast after every app mutation; all were fixed in the second round. Regression coverage: 15 concurrency tests in packages/core (child-process workers importing the built dist), 7 gate/store tests in apps/desktop, and the two old singleton-fallback tests inverted. Full workspace green: 386 desktop, 201 core, 144 mcp tests; pnpm build clean; all four repro harnesses clean post-fix. ADR-0016 records the design; ADR-0013's broken frontmatter (unquoted colon in the summary) was also fixed.

## Open questions

- Windows: renameSync can fail transiently with EPERM under antivirus file holds and writeFileAtomic has no retry; worth a Windows CI pass or a small retry loop if reports arrive.
- Nothing sweeps orphaned .tmp files left by a crash between temp write and rename; harmless and invisible to readers, but a periodic sweep (for example from writePresence's once-per-turn GC) would keep state and entity directories tidy.
- The two-stealer lock race test spawns real child processes and depends on OS scheduling; it passed repeatedly with wide margins but watch CI for flakiness on loaded runners.
- The desktop deferral was verified through the mocked host and the traced Rust watcher chain, not a live two-session GUI run; a manual pass with two Claude Code sessions against a running app would close the loop on mechanisms 1 and 5.
- setActiveTicket(null) clears the per-session marker but the presence beat preserves the entry's previous ticket until the next presence-start, so a cleared ticket lingers on the ring for the rest of the turn; acceptable now, revisit if it confuses.
