## Approach

Diagnose why MCP-created tickets cannot carry markdown bodies despite body support existing somewhere, then fix all layers: delegated implementation to the programmer subagent against a precise brief, audited the diff, gated with a fresh-context verifier, and proved the result end to end by driving the rebuilt MCP server over stdio.

## What happened

Root cause was three-layered: core createTicket has accepted a body since the initial commit (that is the piece that felt already done, wired for the desktop app through the host), but the MCP tool schemas never exposed a body parameter, core updateTicket had no body pathway at all, and unknown field keys passed mutations silently because fields/unknown is a warning while mutations filter to errors, so create dropped a stray body key and update wrote it into frontmatter as junk YAML. The placeholder "(to be written)" bodies came from HEAD-era code defaulting an absent body to a template; the running sidecar binary was built from that. Fix: body parameter on both tools (fields now optional on update_ticket), UpdateTicketInput in core with byte-preserving body handling, unknown-field rejection with a redirect message for body, plus guards the verifier's refutation forced: non-string status rejected instead of silently dropped, empty updates rejected instead of stamping updated, unknown-type tickets get the real cause named while status moves stay legal. Verifier confirmed after one refute-fix round. Full suite green (core 132, desktop 217, mcp 52), build green, sidecars recompiled and the new binary verified to carry the fix. Backfilled real bodies into T-0094, T-0095, T-0096 and T-0098 through the fresh server over stdio, with a live negative probe confirming the rejection path.
