## What happened

Stage 1 (fences.ts refactor, MermaidNode, MERMAID transformer in convert.ts, reconciler tests) passed my audit and boundary attack, but the verifier REFUTED it: the transformer's regExpEnd ignored the opener's fence length, so a 4-plus-backtick fence with a bare ``` line in its body closed early and a zero-edit save corrupted legal CommonMark that the base commit round-tripped byte-identically. Fixed by restricting regExpStart to exactly three backticks so 4-plus-backtick fences keep flowing to the length-aware built-in CODE transformer; the verifier's three repros were added as byte-identity tests and it re-verified the fix CONFIRMED (46-document differential corpus against base, 182 checks, no divergence). Stage 2 (MermaidEditModal, MermaidModalPlugin, BlockEditor/SlashMenu wiring, tokenised CSS, component tests) needed one real deviation: editor.read() instead of editor.getEditorState().read() in the command handler, because insertMermaid's update commit is microtask-deferred and the stale state returned null for the fresh node; also a jsdom Range.getBoundingClientRect stub in test/setup.ts. Final state: 348/348 desktop tests pass, pnpm build green across all packages. Known accepted behaviours, documented in the convert.ts comment: 4-plus-backtick mermaid fences stay CodeNodes in the live editor (read mode still renders them as diagrams); a hand-typed ```mermaid fence stays a CodeNode until the next document load (transformer deliberately outside the typing-shortcut path); normalFormOf is not idempotent for an unclosed heuristic fence at EOF (no byte corruption, reconcile restores original bytes).
