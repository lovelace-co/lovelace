## Approach

Audit every place a version number is declared or consumed across the repository (spec version and app version), then write a detailed ticket for single-sourcing the app version so a store release or software change bumps one value in one place. A scout agent built the file:line map; no code was changed this session.

## What happened

The audit found two distinct version concepts, both currently 0.1.0. The spec version is already single-sourced as SPEC_VERSION in packages/core/src/version.ts, with two drift sites: SPEC.md states the number in three places with no test tying it to the constant, and packages/mcp/src/server.ts:159 hard-codes '0.1.0' in the McpServer declaration. The app version has no single source: it is declared independently in the root and three workspace package.json files, tauri.conf.json and Cargo.toml, with release.yml only checking two of those and only on tag pushes. No UI shows the running app version, and the website repository carries its own CURRENT_VERSION for download buttons. Created T-0129 (parent E-0006, priority medium, moved to todo) specifying: root package.json as the canonical declaration, a scripts/release/sync-version.mjs with version:set and version:check modes, the check wired into PR CI and the release gate extended to all declarations, server.ts reading its version from package.json with a pinning test, the running app version surfaced in General Settings via Tauri's getVersion, a test tying SPEC.md's stated version to SPEC_VERSION, and docs/RELEASING.md documenting the one-command bump. Non-goals lock in that spec version and app version stay separate numbers.
