## Approach

Two-phase orchestration of the Windows failures from release run 29187958890: phase 1, a programmer subagent built the tests-only CI workflow (.github/workflows/test.yml, windows-latest and ubuntu-22.04, workflow_dispatch and ci/** pushes) and produced a root-cause diagnosis of all 85 core failures from the saved job log; phase 2, the same agent implemented the fixes, followed by my audit and a fresh-context adversarial verifier gate before committing.

## What happened

Diagnosis: 83 of 85 failures share one trigger, CRLF checkout on the Windows runner (no .gitattributes, runner autocrlf), through three mechanisms: parseFrontmatter split on LF only and rejected every CRLF entity file (71 failures, a real product bug for Windows users hand-editing tickets); the corrupt() test helper's literal LF patterns silently no-opped on CRLF fixtures (10); two byte-identity tests compared serializer output against the converted checkout (2). The remaining 2 (watchProject double-flush) are unconfirmed, suspected chokidar raw-event timing, and were deliberately left unfixed pending real Windows evidence. Fixes landed in commit b2e06ed: splitLinesWithOffsets in frontmatter.ts (LF, CRLF and bare CR all delimit lines; body recovered by slicing original bytes at an offset so round-trip fidelity holds; writers keep emitting LF as canonical), a .gitattributes pinning text formats to eol=lf with sidecar binaries marked binary, newline-agnostic corrupt() and mutate.spec splitFrontmatter helpers, and a new frontmatter.spec.ts (8 tests, red-first proven). The verifier confirmed both this and the T-0124 change: LF output proven bit-for-bit identical to the old parser across adversarial and 5000 fuzzed inputs, CRLF write path exercised with real updateTicket calls, mutation testing proved the new tests catch regressions. Full serial suite 538 green locally. A validation run of the full suite on real Windows and Linux runners (run 29189510199, branch ci/t-0125-windows-validation) is in progress.
