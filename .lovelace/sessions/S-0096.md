## Approach

Implement ADR-0011's tolerant reads and non-destructive writes: passthrough config parsing with unknown-key warnings, unknown-key preservation through writeSchema with rename tracking, and the SPEC.md 3.1.0 rewrite documenting the semantics. Programmer implemented to a brief; I audited; a fresh-context verifier attacked with a hostile fixture.

## What happened

manifestSchema and every schema.yaml object level now use zod passthrough with known-key sets derived from the shapes; validateSchema warns per unknown key at schema top level, type, status and field (schema/unknown-key), validateProject warns for manifest keys (manifest/unknown-key); mergeField/mergeStatus/mergeType carry unknown keys onto rebuilt nodes in writeSchema; SPEC_VERSION is 3.1.0 with section 4 rewritten to the ADR semantics and a changelog entry; the demo fixture deliberately stays 3.0.0 proving the floor rule. The verifier initially refuted narrowly: a swap or chained rename in one save matched old nodes by name before identity, destroying one node's unknown keys and duplicating another's. Fixed matchOld to resolve identity through the renames map first and to refuse a direct match for a vacated name; added the chain repro as a regression test; the verifier re-confirmed with fresh swap, chain, type-level chain and fresh-node-on-vacated-name attacks, all byte-stable. Also reconciled SPEC wording on field renames (a removal and an addition) and the config comment about the paths object. Full suite green (core 151, desktop 224, mcp 56), build green. Note: the implementing agent once ran git stash on the mixed tree and popped it immediately; I verified stash list empty and both changesets intact afterwards.
