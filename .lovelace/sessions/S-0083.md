## Approach

Analyse how spec versioning is handled across core, host, MCP server and the app, then design a scalable model covering breaking and additive changes plus migrations in both directions (project newer than app, project older than app). Analysis only; no implementation.

## What happened

Traced the whole versioning surface: the single major-equality check in loadManifest collapses too-new and too-old into one dead-end error; the spec's promised minor tolerance is unimplemented (zod strips unknown keys silently and writeSchema rebuilds sections wholesale, destroying newer-minor constructs on save); SPEC_VERSION and SUPPORTED_SPEC_MAJOR are hand-synced; no migration machinery exists (2.x to 3.0 was hand-migrated). Wrote ADR-0011 recording the decided model: major means migrate, minor means additive and tolerated without data loss, patch means prose; one version module and classification helper; typed spec-too-new and spec-needs-migration errors with dedicated screens; spec_version as a floor rewritten only by migrations; a chained plan-and-apply migration registry with the 2.x to 3.0 step as reference and git as the safety net. Cut the work as T-0094 (foundations), T-0095 (tolerant reads, non-destructive writes) and T-0096 (migration framework, depends on T-0094). All three sit in backlog with placeholder bodies since create_ticket cannot write a body.
