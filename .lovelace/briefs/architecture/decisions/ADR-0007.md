# ADR-0007: A Settings home and a read-only Activity group

## Status

Accepted

## Context

The project sidebar groups Board and List under Work, Documentation and Graph under Knowledge, and Sessions, Workflow and Automations under Activity. That last group mixes two things a user does for different reasons: reviewing what happened (Sessions, and the run history inside Automations) and configuring how the project behaves (Workflow, and the rules half of Automations). Because the group mixes modes, tabs read as arbitrary: Workflow has five, Automations has two, Sessions has none. A user cannot predict whether a destination will let them look or change.

Separately, onboarding collects a project name, the user's identity, statuses, types, fields, priorities, the Claude Code integration and a git hook. After onboarding only the middle four (statuses, types, fields, priorities) are editable in the app, through Workflow. The rest have no home at all.

## Decision

Adopt the "Full" consolidation.

- Introduce a single **Settings** destination at the bottom of the sidebar (gear). It holds every configuration surface behind one level of tabs, in the onboarding order and wording: General, Statuses, Types & fields, Automations, Team, Integrations.
- Re-scope **Activity** to read-only history only: Sessions and automation Runs.
- Workflow and Automations stop being top-level destinations. The workflow editor is split into the Statuses tab (statuses and transitions) and the Types & fields tab (types, priorities and fields), which share one draft and one save. Automations splits into a Settings rules tab and a Runs history destination under Activity.
- One rule holds the design together: tabs exist only in Settings. Every other destination is a single flat view.

Settings and the onboarding wizard become the same content in two contexts: the wizard is Settings on first run, Settings is the wizard any time after.

## Consequences

- Configuration gets one predictable home, tabs stop being a wildcard, and the review-versus-configure split becomes explicit. A user learns "tabs mean settings" once.
- Two new validated mutations are needed: writeManifest (rename the project) and writeActors (edit the team). The workflow editor is decomposed into a shared draft hook so two Settings tabs can save as one.
- Actor id rename is out of scope for now: it would need a cascade into tickets, sessions and comments. The Team editor supports add, display-name edit, and remove-if-unreferenced.
- Leaving Settings with an unsaved workflow draft needs a light guard so edits are not silently dropped.
- The Air design system (ADR-0006) is a separate, visual decision; this ADR concerns information architecture only.

Tracked in epic E-0003, delivered across phases T-0059 to T-0063. Nothing visible changes until the routing flip in Phase 4, so the earlier phases land safely on their own.
