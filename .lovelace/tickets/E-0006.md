## Description

Phase 1 of shipping updates to the public. The plumbing already exists: the updater plugin is configured with the https://lovelace.co/releases/latest.json endpoint and a committed pubkey, release builds check on launch, signed update artifacts are emitted, and docs/RELEASING.md documents keys and code signing. What is missing is everything that makes it safe and reliable in strangers' hands:

- The current flow installs silently. On macOS and Linux the update only takes effect at the next relaunch (which for a long-running app may be weeks away); on Windows the installer quits the running app mid-session. Nobody is told anything.
- The check runs once, at launch only.
- Publishing is entirely manual: three platform builds, hand-assembled latest.json, hand uploads. A typo in latest.json silently breaks updates for every install.
- There is no staging step, no written rollback procedure, and no rule for releases that bump the spec major version.

Three tasks close the gap: an in-app restart-to-apply flow, a CI release pipeline on tag push, and a staged publishing process with the release rules written down.

Decision (2026-07-12): lovelace.co/releases is served by the marketing website, the sibling repository at ../website (github.com/lovelace-co/lovelace-website), an Astro static site whose public/ directory ships verbatim. The feed files (releases/latest.json and releases/staging/latest.json) live in that repository under public/releases/, so promoting a release is a git commit plus a website deploy: small, diffable, reversible. The release binaries do not live in the website repository: the macOS update package is already 70MB, several static hosts cap per-file size below that, and committing hundreds of megabytes per release would bloat the repository permanently. The url fields inside latest.json point at the binaries wherever they are hosted (GitHub Releases by default); the updater does not require them to be on the same domain as the feed. The remaining sub-decision (a publicly downloadable home for the binaries) is recorded on T-0117.

## Non-goals

- Beta or preview channels and percentage rollouts (Phase 2; a static feed cannot do percentages).
- Website deployment automation.
- Any telemetry. The update check stays the only network call the app makes.

## Acceptance criteria

- [ ] All three child tasks are done.
- [ ] An end-to-end dry run has been recorded: tag push, CI artifacts, staging feed, a real install updating through the restart-to-apply flow.
