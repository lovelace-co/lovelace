## Description

`writeFileAtomic` (`packages/core/src/fs-atomic.ts`) writes a temp file and renames it over the target. Windows refuses a rename onto a file another handle still has open, so any concurrent reader makes the write throw. The v0.3.0 release run surfaced this on the Windows runner:

```
Error: EPERM: operation not permitted, rename
  '...\.lovelace\state\presence\.stress-session.json.7564.3.tmp'
  -> '...\.lovelace\state\presence\stress-session.json'
```

This is not confined to tests. Every project write in core now goes through `writeFileAtomic`: ticket files, `index.json`, `BOARD.md`, board order, graph layout and presence. The desktop app polls the index while agents mutate, which is exactly the reader that triggers it, so a Windows user can see a mutation fail for no reason the user can act on. POSIX has no equivalent rule, so macOS and Linux never see it.

## Fix

Retry the rename on the transient contention codes Windows reports (`EPERM`, `EACCES`, `EBUSY`) with a short backoff, about 130 ms across twelve attempts, then rethrow. Clean up the temp file when the rename is abandoned.

Two test defects surfaced on the same run and are fixed alongside:

- `writeFileAtomic > preserves the target file mode across a rewrite` asserts POSIX permission bits; Windows models only the read-only bit and reports `0o666` after a chmod to `0o600`. Skipped on Windows.
- The index integrity case asserted the missing-ticket tally before the worker error tallies, so a mutation that failed outright showed up only as the symptom it caused. Reordered.

## Acceptance criteria

- The Windows leg of the `test` workflow passes.
- `pnpm test` and `pnpm build` pass on macOS.
- A rename failure that is not transient contention still throws, and leaves no temp file behind.
