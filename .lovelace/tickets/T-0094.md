## Description

The tooling collapses "project newer than the app" and "project older than the app" into one refusal: loadManifest throws the same ConfigError whenever the manifest's major differs from SUPPORTED_SPEC_MAJOR, and SPEC_VERSION and SUPPORTED_SPEC_MAJOR are two hand-synced constants. The two situations need opposite remedies. [[ADR-0011]] records the decided model.

Foundations to build:

- One version module in packages/core: SPEC_VERSION is the single source, the supported major is derived from it, and a classification helper compares a project's declared version with the tooling and returns too-new, needs-migration or ok.
- ConfigError carries a machine code (spec-too-new or spec-needs-migration) plus both versions. The host serialises the code; the MCP server and agent helper report the same classification in their error text and direct agents to open the project in the app.
- The app switches on the code instead of pattern-matching message strings: spec-too-new renders a dedicated screen naming both versions and pointing at the app update; spec-needs-migration shows the migration entry screen (a placeholder until [[T-0096]] lands).

## Acceptance criteria

- [ ] SUPPORTED_SPEC_MAJOR is derived from SPEC_VERSION, never declared separately.
- [ ] Opening a project with a higher major shows the update-Lovelace screen naming both versions.
- [ ] Opening a project with a lower major surfaces the spec-needs-migration code, distinct from too-new.
- [ ] The MCP server and agent helper emit the classification in their error text.
- [ ] Tests cover both directions with corrupted-manifest fixtures; pnpm test and pnpm build green.
