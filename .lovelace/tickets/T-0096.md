## Description

No migration machinery exists; the 2.x to 3.0 break was hand-migrated in this repository, and an outside user's older project is refused with no pathway. Build the framework decided in [[ADR-0011]]: a registry in packages/core with one step per major boundary, each step declaring the majors it upgrades from and to, a plain-English summary, a plan (dry run listing which files change and how) and an apply. Steps chain so a project several majors behind migrates stepwise. After apply the framework stamps spec_version, reloads, runs full validation and reindexes; a post-migration validation failure is reported, never silently repaired. Git is the safety net rather than bespoke backup machinery: the confirm screen instructs the user to commit first. The migration floor is 2.x, with the 2.x to 3.0 step shipping as the reference implementation.

In the app, the spec-needs-migration screen from [[T-0094]] lists each pending step's summary, the commit-first note, and one primary action; on success the project reloads normally.

## Acceptance criteria

- [ ] A 2.x fixture project migrates to 3.0 through the app flow and passes full validation.
- [ ] Migrated files keep comments and produce minimal diffs (document patching, not rewrites).
- [ ] A project below the floor gets an honest refusal naming the floor.
- [ ] Running the migration on an already-current project is refused as already current.
- [ ] Each step has fixtures: a project in the old format, a snapshot of the migrated output, and a validation pass over the result.
