## Description

Add an OpenCode integration to the desktop app so projects can be wired up to the OpenCode agent the same way they are wired up to Claude Code today. It appears in Settings, Integrations, alongside the Claude Code card, and follows the exact same behaviours: the same three install states, the same install and reinstall flow, the same file ownership rules (marker-delimited sections, merge without clobbering), the same agent helper wiring, and the same test coverage bar.

The Claude Code integration is the reference implementation. Its behaviour lives in `packages/mcp/src/claude.ts` (install and detect), `packages/mcp/src/helper.ts` (the seven hook subcommands), `apps/desktop/src/components/IntegrationsSettings.tsx` (the card UI), `packages/mcp/src/host.ts` (the `detect_claude` and `install_claude` ops) and is pinned by `packages/mcp/test/claude.spec.ts` and `apps/desktop/test/views.spec.tsx`. Every behaviour listed below names its Claude counterpart; "same as Claude Code" means byte-level equivalent behaviour, not approximately similar.

## UI: Settings, Integrations tab

- The Integrations tab shows an OpenCode card next to the existing Claude Code card. Update the tab hint copy so it no longer names only Claude Code.
- Same three states as the Claude card: not installed ("OpenCode assets are not installed", button "Install OpenCode assets"); partially installed (lists the missing pieces, for example "Missing: MCP server, Hooks, Commands", button "Install OpenCode assets"); fully installed ("OpenCode assets are installed", the "installed" badge, button "Reinstall OpenCode assets").
- Same result rendering: after install, show the `written` file list and any `manual` steps the user must do by hand.
- The Git hook checkbox behaviour is shared: the `prepare-commit-msg` hook is agent-agnostic (it reads `.lovelace/state/active_ticket`), so either card may install it and the second install must detect it is already present rather than duplicating it.
- All the settled design conventions apply (control species, tonal surfaces, sans for all copy); the OpenCode card must be visually identical in structure to the Claude card, not a redesign.

## Host operations

- Two new host ops mirroring the Claude pair: `detect_opencode` returning an `OpenCodeInstallStatus` object with the same shape philosophy as `ClaudeInstallStatus` (per-piece booleans plus an overall `installed` that is true only when all core pieces are present), and `install_opencode` taking the project root and the `gitHook` flag, returning `{ written: string[], manual: string[] }`.
- Client wiring in `apps/desktop/src/lib/host.ts` mirroring `installClaude` and `claudeStatus`.
- Binary paths resolve exactly as Claude's do, through the existing sibling-command resolution in `host.ts` (compiled `lovelace-mcp` and `lovelace-agent` sidecars, `node dist/...` fallback in dev). No new path scheme.

## Files written on install

Mirror each Claude asset with its OpenCode equivalent. All merge and ownership rules are identical to `claude.ts`:

1. **MCP registration** in OpenCode's project config file: add a `lovelace` MCP server entry pointing at the MCP server binary with `LOVELACE_ROOT` set to the project root, merged into any existing config, preserving every unrelated key the user already has (Claude counterpart: the `mcpServers.lovelace` entry in `.mcp.json`). Malformed existing JSON is never overwritten: report a manual step with the exact snippet to paste, same as Claude's behaviour.
2. **Agent instructions**: OpenCode reads `AGENTS.md` natively. Write the Lovelace section into the project root `AGENTS.md` wrapped in the same `<!-- lovelace:start -->` and `<!-- lovelace:end -->` markers, replacing only the delimited section on reinstall and never touching user content outside it (Claude counterpart: the `CLAUDE.md` section). The section points at `.lovelace/AGENTS.md`, which is created or refreshed exactly as today; that file is shared between integrations, so the second install refreshes rather than duplicates it.
3. **Commands**: OpenCode's equivalent of the two slash commands, `ticket` and `done`, with the same steps as `.claude/commands/ticket.md` and `done.md` (load ticket by argument, read dependencies and docs, set active ticket, move to in progress; check criteria, move by outcome, log session, clear active). Written in OpenCode's command format and location.
4. **Hooks**: wire the agent helper's seven behaviours to OpenCode's session and tool lifecycle, calling the same `lovelace-agent` binary subcommands used by Claude hooks: `digest` at session start, `session-check` at stop (blocking the finish when the ticket or session record is unresolved, if OpenCode supports blocking), `guard` before file edits (rejecting direct edits to `.lovelace/tickets/*`), `presence-start` at prompt submit, `presence-beat` after tool calls, `track-active` after `set_active_ticket`, `presence-clear` at session end. The per-session presence model of ADR-0012 must keep working with OpenCode session IDs.
5. **Git hook** (opt-in, checkbox): the existing agent-agnostic `prepare-commit-msg` script, only when `.git/` exists; if a non-Lovelace hook file already exists, report a manual step with the snippet to append, same as today.

Cross-platform rules carry over unchanged: paths written with forward slashes so they survive bash on Windows, quoting only where a shell will parse the command, no quoting inside plain JSON config, and the same idempotency bar: installing twice produces byte-identical files, and hook or config entries are deduplicated by content before appending.

## Mapping investigation (do this first, record an ADR)

Claude Code's hook events and OpenCode's extension surface (its config schema, plugin or hook events, command format and file locations) are not one-to-one. Before implementing, verify against the current OpenCode documentation: the exact project config filename and MCP schema, where commands live and their frontmatter, which lifecycle events exist, whether a stop can be blocked the way `session-check` blocks Claude's Stop hook with exit code 2, and what payload shape the events deliver (the helper may need a thin payload adapter if OpenCode's JSON differs from Claude's hook payloads; adapt in the integration layer, do not fork the helper's behaviours). Record the mapping table, and any behaviour that cannot be reproduced (with its documented manual fallback), as an ADR in `.lovelace/documentation/architecture/decisions/`. A behaviour silently dropped is a failed acceptance; a behaviour OpenCode cannot express must be listed in the ADR and surfaced as a `manual` step or documented limitation.

## Detection

`detect_opencode` mirrors `detectClaudeAssets`: read-only, silent on missing files and malformed JSON (malformed means not installed, never a throw), checking the MCP entry, the hook or plugin wiring by content (the known helper subcommand suffixes), the command files' existence, and the marker presence in root `AGENTS.md` and `.lovelace/AGENTS.md`, plus the shared Git hook by its 'Lovelace' marker.

## Code structure

Extract what is genuinely shared rather than copying `claude.ts` wholesale: the marker section replace, the merge-preserving JSON edit, the manual-step reporting shapes and the `.lovelace/AGENTS.md` template are integration-agnostic and should be shared with the Claude implementation without changing its behaviour. Keep per-agent specifics (file names, config schema, event wiring) in a new `opencode.ts` beside `claude.ts`. Do not change any Claude Code behaviour in this ticket; its existing tests must pass untouched.

## Tests

Same coverage bar as the Claude integration:

- `packages/mcp`: a `opencode.spec.ts` mirroring `claude.spec.ts`: clean install writes everything with no manual steps; reinstall is byte-identical (idempotency); merging preserves the user's unrelated config keys and existing entries; Windows backslash paths normalise to forward slashes with correct quoting; each partial-install state reports correctly; malformed JSON is treated as not installed and produces a manual step on install; marker detection requires the markers, not just the file.
- `apps/desktop`: component tests mirroring the Claude card tests: the three states render with the right copy and buttons, install calls the host with the git hook flag, the badge appears only when fully installed, and `written` and `manual` results render. Extend `test/fakeHost.ts` with the OpenCode ops.
- Existing Claude tests pass unchanged.

## Acceptance criteria

- In a project with neither integration, both cards show not installed; installing OpenCode assets produces a working setup: OpenCode in that project sees the Lovelace MCP server and its eight tools, receives the digest at session start, is blocked from editing `.lovelace/tickets/*` directly, has working `ticket` and `done` commands, and presence markers appear and clear per session.
- In a project that already has the Claude Code integration, installing OpenCode does not disturb any Claude asset, does not duplicate `.lovelace/AGENTS.md` content or the Git hook, and both cards report installed.
- Reinstalling OpenCode assets twice produces byte-identical files.
- The mapping ADR exists and names any Claude behaviour OpenCode cannot reproduce, with its fallback.
- `pnpm test` and `pnpm build` pass.

## Non-goals

- No changes to the Claude Code integration's behaviour or file formats.
- No new MCP tools; the server keeps exactly its eight tools.
- No other agent integrations (Cursor, Gemini CLI and similar are separate tickets).
- No global (user-level) OpenCode configuration; project-level wiring only, matching the Claude integration's scope.
