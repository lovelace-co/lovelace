## Description

Add a Codex (OpenAI Codex CLI) integration to the desktop app so projects can be wired up to Codex the same way they are wired up to Claude Code and OpenCode today. It appears in Settings, Integrations, alongside the existing cards, and follows the exact same behaviours: the same three install states, the same install and reinstall flow, the same file ownership rules (marker-delimited sections, merge without clobbering), the same agent helper wiring, and the same test coverage bar.

The Claude Code integration is the reference implementation; the OpenCode integration (T-0150, ADR-0014, shipped in 0.2.0) is the reference for how to add another agent on top of the shared machinery. Behaviour lives in `packages/mcp/src/claude.ts` and `packages/mcp/src/opencode.ts` (install and detect), the shared `packages/mcp/src/assets.ts` (marker sections, merge-preserving JSON edits, the `.lovelace/AGENTS.md` template, the Git hook), `packages/mcp/src/helper.ts` (the seven hook subcommands, which must not be forked), `apps/desktop/src/components/IntegrationsSettings.tsx` (the generic `IntegrationCard`), and `packages/mcp/src/host.ts` (the detect and install ops). These are pinned by `packages/mcp/test/claude.spec.ts`, `packages/mcp/test/opencode.spec.ts` and `apps/desktop/test/views.spec.tsx`. "Same as Claude Code" means byte-level equivalent behaviour, not approximately similar.

## UI: Settings, Integrations tab

- The Integrations tab shows a Codex card next to the existing cards, rendered through the existing generic `IntegrationCard`, not a new component.
- Same three states: not installed ("Codex assets are not installed", button "Install Codex assets"); partially installed (lists the missing pieces, for example "Missing: MCP server, Hooks, Commands", button "Install Codex assets"); fully installed ("Codex assets are installed", the "installed" badge, button "Reinstall Codex assets").
- Same result rendering: after install, show the `written` file list and any `manual` steps the user must do by hand.
- The Git hook checkbox behaviour is shared: the `prepare-commit-msg` hook is agent-agnostic, so any card may install it and later installs must detect it is already present rather than duplicating it.
- All the settled design conventions apply (control species, tonal surfaces, sans for all copy); the Codex card must be visually identical in structure to the existing cards, not a redesign.

## Host operations

- Two new host ops mirroring the existing pairs: `detect_codex` returning a `CodexInstallStatus` object with the same shape philosophy as `ClaudeInstallStatus` (per-piece booleans plus an overall `installed` that is true only when all core pieces are present), and `install_codex` taking the project root and the `gitHook` flag, returning `{ written: string[], manual: string[] }`.
- Client wiring in `apps/desktop/src/lib/host.ts` mirroring `installClaude` and `claudeStatus`.
- Binary paths resolve exactly as the existing integrations' do, through the existing sibling-command resolution in `host.ts`. No new path scheme.

## Files written on install

Mirror each asset with its Codex equivalent. All merge and ownership rules are identical to `claude.ts` and `opencode.ts`, using the shared machinery in `assets.ts`:

1. **MCP registration** in Codex's config: a `lovelace` MCP server entry pointing at the MCP server binary with `LOVELACE_ROOT` set to the project root, merged into any existing config, preserving every unrelated key the user already has. Codex configuration is TOML (`config.toml`), not JSON, so the merge-preserving edit needs a TOML-aware equivalent of `mergeJsonFile` with the same guarantee: malformed existing config is never overwritten, report a manual step with the exact snippet to paste instead. Whether Codex supports project-level MCP registration at all is a mapping-investigation question (see below); if registration can only live in the user-level `~/.codex/config.toml`, the ADR must decide the approach and the install must surface it honestly (most likely a `manual` step carrying the exact TOML snippet, since the installer's project-scope rule forbids writing outside the repository).
2. **Agent instructions**: Codex reads `AGENTS.md` natively (it originated the convention). Write the Lovelace section into the project root `AGENTS.md` wrapped in the same `<!-- lovelace:start -->` and `<!-- lovelace:end -->` markers, replacing only the delimited section on reinstall and never touching user content outside it. The section points at `.lovelace/AGENTS.md`, which is created or refreshed exactly as today; that file and the root `AGENTS.md` section are shared between integrations (OpenCode already writes the same section), so installs on top of each other refresh rather than duplicate.
3. **Commands**: Codex's equivalent of the two slash commands, `ticket` and `done`, with the same steps as `.claude/commands/ticket.md` and `done.md` (load ticket by argument, read dependencies and docs, set active ticket, move to in progress; check criteria, move by outcome, log session, clear active). Written in Codex's prompt format and location as verified by the investigation.
4. **Hooks**: wire as many of the agent helper's seven behaviours as Codex's lifecycle surface can express, calling the same `lovelace-agent` binary subcommands: `digest` at session start, `session-check` at stop, `guard` before file edits (rejecting direct edits to `.lovelace/tickets/*`), `presence-start` at prompt submit, `presence-beat` after tool calls, `track-active` after `set_active_ticket`, `presence-clear` at session end. Codex's hook surface is expected to be much narrower than Claude Code's or OpenCode's; the investigation decides what is expressible. Any payload adaptation lives in the integration layer; do not fork the helper's behaviours. The per-session presence model of ADR-0012 must keep working with Codex session IDs where presence can be wired at all.
5. **Git hook** (opt-in, checkbox): the existing agent-agnostic `prepare-commit-msg` script via the shared `writeGitHook`, only when `.git/` exists; if a non-Lovelace hook file already exists, report a manual step with the snippet to append, same as today.

Cross-platform rules carry over unchanged: paths written with forward slashes so they survive bash on Windows, quoting only where a shell will parse the command, no quoting inside plain config files, and the same idempotency bar: installing twice produces byte-identical files, and config entries are deduplicated by content before appending.

## Mapping investigation (do this first, record an ADR)

Codex's extension surface differs substantially from both Claude Code's hooks and OpenCode's plugins, and it moves quickly. Before implementing, verify against the current Codex documentation and record the mapping table as an ADR in `.lovelace/documentation/architecture/decisions/`, following ADR-0014's shape. Questions the ADR must answer:

- The exact config file name, format and location, and whether project-level configuration (a repository-local config that Codex picks up) exists for MCP servers, or only the user-level `~/.codex/config.toml`. If project-level MCP registration is impossible, decide and record the fallback.
- The MCP server entry schema in that config (command, args, env) and how Codex launches stdio MCP servers.
- Where custom prompts or commands live, their format and frontmatter, whether they support arguments, and whether a project-level location exists.
- Which lifecycle or hook events exist at all (historically Codex offered little beyond a `notify` hook for turn completion); whether any tool-call interception exists that could express `guard`; whether anything can block a stop the way `session-check` blocks Claude's Stop hook; whether session start context injection exists for `digest`.
- What payload each expressible event delivers, and the thin adapter needed to feed the helper its Claude-shaped stdin.

A behaviour silently dropped is a failed acceptance; a behaviour Codex cannot express must be listed in the ADR with its documented manual fallback or degradation, exactly as ADR-0014 names OpenCode's three degradations. Expect the degraded list to be longer here; that is acceptable as long as every gap is named, bounded and user-visible. If the investigation concludes that `guard` cannot be expressed at all, the fallback must at minimum keep the instruction-level rule (`.lovelace/AGENTS.md` forbids direct ticket edits) and the ADR must say the enforcement is advisory for Codex.

## Detection

`detect_codex` mirrors `detectClaudeAssets` and the OpenCode detector: read-only, silent on missing files and malformed config (malformed means not installed, never a throw), checking the MCP entry, any hook or notify wiring by content (the known helper subcommand suffixes), the command or prompt files' existence, the marker presence in root `AGENTS.md` and `.lovelace/AGENTS.md`, plus the shared Git hook via the shared `detectGitHook`. Pieces the ADR rules out as inexpressible are excluded from the `installed` calculation rather than reported forever-missing.

## Code structure

Build on `packages/mcp/src/assets.ts`; extend it only with genuinely integration-agnostic additions (for example a TOML merge helper mirroring `mergeJsonFile`, if the format question lands on TOML). Keep per-agent specifics (file names, config schema, event wiring) in a new `codex.ts` beside `claude.ts` and `opencode.ts`. Do not change any Claude Code or OpenCode behaviour in this ticket; their existing tests must pass untouched.

## Tests

Same coverage bar as the existing integrations:

- `packages/mcp`: a `codex.spec.ts` mirroring `opencode.spec.ts`: clean install writes everything with no unexpected manual steps; reinstall is byte-identical (idempotency); merging preserves the user's unrelated config keys and existing entries; Windows backslash paths normalise to forward slashes with correct quoting; each partial-install state reports correctly; malformed config is treated as not installed and produces a manual step on install; marker detection requires the markers, not just the file; installing alongside existing Claude and OpenCode assets mutates none of them.
- `apps/desktop`: component tests mirroring the existing card tests: the three states render with the right copy and buttons, install calls the host with the git hook flag, the badge appears only when fully installed, and `written` and `manual` results render. Extend `test/fakeHost.ts` with the Codex ops.
- Existing Claude and OpenCode tests pass unchanged.

## Acceptance criteria

- In a project with no integrations, all cards show not installed; installing Codex assets produces a working setup within what the ADR says Codex can express: Codex in that project sees the Lovelace MCP server and its eight tools (via project config or the documented manual step), reads the Lovelace instructions from `AGENTS.md`, and has working `ticket` and `done` commands.
- Every helper behaviour the ADR maps as expressible works; every one it cannot express is named in the ADR with its fallback and, where install-time action is needed, surfaced as a `manual` step.
- In a project that already has the Claude Code or OpenCode integration, installing Codex does not disturb any existing asset, does not duplicate the root `AGENTS.md` section, `.lovelace/AGENTS.md` content or the Git hook, and all installed cards report installed.
- Reinstalling Codex assets twice produces byte-identical files.
- The mapping ADR exists and names every behaviour Codex cannot reproduce, with its fallback.
- `pnpm test` and `pnpm build` pass.

## Non-goals

- No changes to the Claude Code or OpenCode integrations' behaviour or file formats.
- No new MCP tools; the server keeps exactly its eight tools.
- No other agent integrations (Cursor, Gemini CLI and similar are separate tickets).
- No writes outside the repository: the installer never edits `~/.codex/`; anything that must live there becomes a `manual` step with the exact snippet.
