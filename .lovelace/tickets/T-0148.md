## Description

VS Code and similar desktop tools offer a one-click way to put their command-line entry point on the user's PATH ("Shell Command: Install 'code' command in PATH"). Lovelace should offer the same, so users can invoke Lovelace from a terminal without digging into the app bundle or install directory.

Today the binaries ship inside the app (the desktop app plus the bundled sidecars: the MCP server, the agent helper and the core host) and nothing is reachable from a shell by name. Anyone wiring up Claude Code hooks or an MCP configuration by hand has to find the install path themselves, and it differs per platform and per install.

Add an action in the app (for example in settings, mirroring VS Code's command palette entry) that registers the command on the PATH, and a matching action to remove it.

## Requirements

- One-click install and uninstall from within the app; report clearly whether it worked, and surface a clear error when elevation is refused or the target directory is not writable.
- macOS: symlink into a directory already on the PATH (`/usr/local/bin` when writable, otherwise fall back to `~/.local/bin` and say so). Do not require the app to run elevated; prompt only for the single operation if needed.
- Windows: add the install location to the user-level PATH (registry, no elevation), the way VS Code's installer does.
- Linux: symlink into `~/.local/bin` (creating it is fine); note in the success message if that directory is not on the user's PATH.
- Idempotent: running install twice is safe; a stale link from a previous install location is repaired, not duplicated.
- The app must keep working if the user never registers the command; nothing else may depend on it.
- Survives app updates: the registered command must not break when the app updates in place.

## Open question to settle at implementation

Which command gets registered. The brief rules out a standalone user-facing CLI in the MVP, so the candidates are a launcher that opens the app (closest to what `code` does) and/or exposing the existing agent-facing sidecars (MCP server, agent helper) by a stable name so hook and MCP configs can reference them portably. Decide the scope before briefing the work and record the choice (ADR if it shapes the product surface).

## Acceptance criteria

- After the install action, opening a fresh terminal and running the registered command works on macOS and Windows.
- The uninstall action removes exactly what install created.
- Running install twice leaves a single working registration.
- `pnpm test` and `pnpm build` pass.

## Non-goals

- No new user-facing CLI surface (commands, flags, subcommands) beyond making the existing entry point reachable; the MVP brief excludes a standalone CLI.
- No system-wide/all-users installation and no persistent elevation.
- No shell completion or man pages.
