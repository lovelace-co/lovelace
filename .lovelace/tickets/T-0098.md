## Description

create_ticket offered no way to write the markdown body (its input schema stopped at type and fields) and core updateTicket had no body pathway at all; the desktop app wrote bodies through a raw host op instead. Unknown field keys passed mutations silently because fields/unknown is only a warning and mutations filter to errors: create dropped them, and update wrote them into frontmatter, so a stray body key became a junk body: frontmatter field.

Fixed by:

- A body parameter on create_ticket and update_ticket, forwarded to core; fields is now optional on update_ticket so a body-only edit needs no empty object.
- updateTicket takes UpdateTicketInput with body support mirroring createTicket's blank-body handling; an omitted body preserves the existing body bytes exactly.
- Mutations reject unknown field keys with an error listing the defined fields; a stray body key redirects to the body parameter.
- Guards found under adversarial verification: an update carrying neither fields nor a body is rejected instead of rewriting the file to stamp updated; a non-string status is rejected instead of silently dropped; field edits on a hand-edited unknown type name the real cause while status moves stay legal so the ticket can still be parked.

## Acceptance criteria

- [x] create_ticket and update_ticket accept body and advertise it in their input schemas.
- [x] Unknown fields are rejected on create and update with the defined-field list.
- [x] Round-trip: fields-only updates leave body bytes identical; body-only updates leave frontmatter identical apart from updated.
- [x] pnpm test and pnpm build green; fresh-context verifier attacks confirmed.
