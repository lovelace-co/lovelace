## Description

The pipeline (T-0116) stops at a draft GitHub Release; this task defines how a release reaches users, with one manual gate between CI output and every public install. The feed is served by the marketing website (the sibling repository at ../website, github.com/lovelace-co/lovelace-website): its public/ directory ships verbatim, so the feed files live at public/releases/ there and every promotion is a git commit plus a deploy.

- Staging: commit the CI-generated latest.json to public/releases/staging/latest.json in the website repository and deploy. Its url fields already point at the publicly hosted binaries. A real install pointed at the staging feed through the endpoint override (T-0115) must update through the restart-to-apply flow before anything goes live.
- Promotion: copy the staged latest.json over public/releases/latest.json, update CURRENT_VERSION and the PLATFORMS download links in src/consts.ts so the site's download buttons track the release, commit and deploy. One commit is the single deliberate act that ships an update, and reverting that commit un-ships it for anyone not yet updated.
- Binary hosting (sub-decision to resolve here): the update packages and installers are ~70MB per platform and stay out of both git repositories. Default is GitHub Releases; the assets must be publicly downloadable, so either the monorepo's releases are public or a dedicated public releases repository holds them. The website host is an alternative only if its per-file limit clears the artifact sizes.
- Rollback: the updater only offers versions greater than the one running, so rolling back means shipping a new, higher version that contains the previous code. Write the exact procedure down, including the version arithmetic.
- Spec-major rule: a release that bumps the SPEC.md major version is never routine. Its notes must say projects will be offered a migration on next open, and the release checklist must name the rule.
- Rewrite docs/RELEASING.md around the pipeline: what CI owns, what stays manual (the staging commit, verification, the promotion commit), rollback, the spec-major rule. Key handling and rotation stay as documented.

## Non-goals

- No automation of the promotion step; the gate stays human.
- No beta channel (Phase 2).
- No website redesign work; only the releases directory and the consts the download buttons read.

## Acceptance criteria

- [ ] docs/RELEASING.md describes the full path from tag push to live latest.json, including the staging commit, verification and the promotion commit in the website repository.
- [ ] The rollback procedure is documented and mechanically correct (a higher version carrying the previous code).
- [ ] The spec-major rule appears in the release checklist.
- [ ] The binary hosting decision is made and recorded, and the promoted feed's url fields resolve publicly.
- [ ] The website's download buttons point at the promoted installers after promotion.
- [ ] One full dry run is recorded: tag, CI artifacts, staging feed deployed, a real install updating from staging, stopping short of live promotion.
- [ ] pnpm test and pnpm build pass.
