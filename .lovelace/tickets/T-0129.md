## Description

The application release version (currently `0.1.0`) is declared independently in six files, with only a partial release-time CI gate keeping some of them aligned. Bumping the version for a store release means editing four to six files by hand and hoping CI catches a miss. One consumer already hard-codes the number in source and will silently drift. Nothing in the running app displays its own version.

This task makes the app version a single controlled value: set it in one place, propagate it everywhere with one command, and fail CI when any site disagrees.

## Two versions, kept separate

The repository carries two distinct version concepts. They must not be unified; they change for different reasons at different cadences:

- The spec (file format) version is a contract over `.lovelace/` content, governed by ADR-0011. It is already single-sourced as `SPEC_VERSION` in `packages/core/src/version.ts` (with `SUPPORTED_SPEC_MAJOR` derived from it) and bumps only when the format changes.
- The app (release) version is what users see in the stores and what the updater compares. It bumps on every release, including releases that change no format at all.

This task single-sources the app version. The spec version keeps its existing constant; the only spec-version work here is closing its two drift sites (see the side item below).

## Inventory of current app-version sites

Declarations, all carrying the literal `0.1.0` today:

- `package.json` (root, line 4)
- `packages/core/package.json` (line 3)
- `packages/mcp/package.json` (line 3)
- `apps/desktop/package.json` (line 3)
- `apps/desktop/src-tauri/tauri.conf.json` (line 5)
- `apps/desktop/src-tauri/Cargo.toml` (line 3), with `Cargo.lock` pinning the same number for `lovelace-desktop`

Consumers and enforcement:

- `packages/mcp/src/server.ts` line 159 hard-codes `version: '0.1.0'` in the `McpServer` declaration instead of reading it from anywhere. This is the site most likely to drift unnoticed.
- `.github/workflows/release.yml` lines 73 to 78 gate a release on tag == tauri.conf.json version == root package.json version. The workspace package.json files, `Cargo.toml` and `server.ts` are unchecked, and the gate only runs on tag pushes, never on PRs.
- `.github/workflows/release.yml` also stamps the version into artifact names (the DMG filename) and `scripts/release/latest-json.mjs` stamps it into the update feed via its `--version` argument. These read the version at release time and are fine as consumers; they just need the declarations they read to be trustworthy.
- No UI shows the running app version. `apps/desktop/src/components/GeneralSettings.tsx` line 136 shows the open project's `spec_version`, which is a different number with a different meaning.
- The marketing website repository (`../website`, see T-0117) carries its own `CURRENT_VERSION` in `src/consts.ts` for the download buttons. It is outside this repository and stays a manual step on the release checklist; it is named here so the checklist names every site.

## Proposed mechanism

Simpler wins: no build-time codegen, no new dependencies, no release automation. The root `package.json` `version` field becomes the canonical declaration, and a small script propagates and polices it.

1. Add `scripts/release/sync-version.mjs` with two modes, exposed as root scripts:
   - `pnpm version:set <x.y.z>`: validates the argument is plain semver, then writes the root `package.json`, the three workspace `package.json` files, `apps/desktop/src-tauri/tauri.conf.json` and `apps/desktop/src-tauri/Cargo.toml`, then refreshes `Cargo.lock` (for example `cargo update --workspace` scoped to the `lovelace-desktop` package, or an equivalent minimal touch). Edits must be minimal and preserve each file's existing formatting; JSON files keep their indentation and key order, and the Cargo.toml edit replaces only the version value.
   - `pnpm version:check`: exits non-zero and lists every out-of-sync file when any declaration disagrees with the root `package.json`. Zero output changes on success so it is CI-friendly.
2. Wire `pnpm version:check` into CI on every pull request, and extend the existing tag gate in `release.yml` so a release verifies all six declarations, not two. The tag must still equal `v` plus the canonical version.
3. Stop hard-coding the version in `packages/mcp/src/server.ts`: read it from `packages/mcp/package.json` (Node 22 JSON module import, or a small constant kept honest by a test; implementer's choice, whichever survives the Bun sidecar compile). Add a test asserting the `McpServer` declared version equals the package version.
4. Surface the running app version in the desktop app: show it in General Settings (or the About surface) via Tauri's version API (`getVersion()` from `@tauri-apps/api/app`), clearly distinguished from the project's spec version. Follow the design conventions: sans type, no raw machine identifiers.
5. Document the bump procedure in `docs/RELEASING.md`: one `pnpm version:set` call, commit, tag `v<version>`, and the manual website `CURRENT_VERSION` update at promotion time (coordinates with T-0117's checklist).

## Spec-version side item

Close the two drift sites of the spec version while in here:

- Add a test asserting that every version number stated in `SPEC.md` (the title line, the prose statement and the `spec_version` example) matches `SPEC_VERSION` from `packages/core/src/version.ts`, so the document cannot drift from the constant.
- The manifest fixtures (`.lovelace/manifest.yaml`, `examples/demo-project/.lovelace/manifest.yaml`) are already covered by existing tests; no change expected there.

## Non-goals

- No unification of spec version and app version into one number.
- No changes to the staged publishing design; T-0117 owns the feed, promotion gate and rollback.
- No automation of the website repository's `CURRENT_VERSION`; it stays a named manual step.
- No new versioning or ID schemes, no prerelease channels, no automatic bump-on-merge.
- The sync script never touches `.lovelace/` content or any file the round-trip guarantee covers.

## Outcome

Shipped in commit 1922a00. Implementation notes against the proposal above:

- The chosen server-version mechanism is a small constant, `APP_VERSION` in `packages/mcp/src/version.ts`, managed by the sync script and pinned to `packages/mcp/package.json` by `packages/mcp/test/version.spec.ts`. The Bun sidecar compile was verified with the import in place.
- Cargo.lock is edited directly by the script (the `lovelace-desktop` `[[package]]` block only), so no Rust toolchain is needed for a bump. The round trip `version:set 0.2.0` then `version:set 0.1.0` restores byte-identical files, verified by content hash.
- The app version renders as a quiet sans footer line ("Lovelace 0.1.0") at the bottom of General settings, deliberately away from the project facts grid where the spec version lives.
- The last criterion is half-met: `pnpm build` passes, and every suite touching this change is green (desktop 350/350, the new core and mcp tests pass). The root `pnpm test` is red for a pre-existing reason unrelated to this ticket: the demo fixture gained `T-0005` in commit 72fd60e without the hard-coded test expectations moving with it.
