# ADR-0015: Mapping the agent integration onto Codex

## Status

Accepted. Implementation is tracked as [[T-0152]].

## Context

The Claude Code integration wires a project up with four kinds of asset: the MCP server entry in `.mcp.json`, a marker-delimited section in `CLAUDE.md` that inlines `.lovelace/AGENTS.md`, two slash commands, and seven hook commands that call the `lovelace-agent` helper (`digest`, `session-check`, `guard`, `presence-start`, `presence-beat`, `track-active`, `presence-clear`). [[T-0152]] adds the same integration for OpenAI's Codex CLI, following the OpenCode precedent ([[ADR-0014]]).

Facts verified against the Codex documentation (developers.openai.com/codex and the openai/codex repository, rust-v0.145.0 series, July 2026): configuration is TOML; project-level `.codex/config.toml` files are loaded for trusted projects and honour MCP server registration (`[mcp_servers.<name>]` with `command`, `args`, `env`); Codex reads the project root `AGENTS.md` natively (global, then root down to the working directory, 32 KiB combined default) with no include mechanism; custom prompts are deprecated, user-level only, and replaced by repo-shareable skills (`.agents/skills/<name>/SKILL.md` with `name` and `description` frontmatter, invoked as `$name`); and Codex now ships a full hooks framework (`hooks.json` or `[hooks]` tables in any config layer) with events `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop` and others. Hook commands receive a Claude-shaped JSON payload on stdin (`session_id`, `hook_event_name`, `tool_name`, `tool_input`), `PreToolUse` and `Stop` block on exit code 2 with the reason on stderr, and `SessionStart` stdout is injected as developer context. Two trust gates apply: project `.codex/` layers load only for trusted projects, and each command hook must be reviewed and trusted by the user (`/hooks` in the TUI), re-trusted whenever the hook definition changes.

## Decision

One asset set per concern, all owned the same way as the Claude and OpenCode assets (marker-delimited or wholly managed files, merge-preserving edits, byte-identical reinstalls):

| Claude Code asset | Codex equivalent |
| --- | --- |
| `mcpServers.lovelace` in `.mcp.json` | `[mcp_servers.lovelace]` in `.codex/config.toml`: `command`, `args` (the same `parseCommand` split), `env.LOVELACE_ROOT = "."`, written as a `# lovelace:start` / `# lovelace:end` comment-delimited section |
| `CLAUDE.md` section with the `@.lovelace/AGENTS.md` include | A marker-delimited section in the root `AGENTS.md` (read natively) directing the agent to read `.lovelace/AGENTS.md`; Codex has no include mechanism, so the pointer is a directive rather than an automatic inclusion |
| `.claude/commands/ticket.md`, `done.md` | Skills at `.agents/skills/ticket/SKILL.md` and `.agents/skills/done/SKILL.md`, same steps, `name` and `description` frontmatter, invoked as `$ticket` / `$done` (custom prompts are deprecated and cannot ship in the repository) |
| Seven hook commands in `.claude/settings.json` | Seven hook commands in `.codex/hooks.json`, same `{ matcher?, hooks: [{ type: "command", command }] }` entry shape, calling the same `lovelace-agent` subcommands with no payload adapter |
| `prepare-commit-msg` Git hook | Shared unchanged; any integration installs it, each detects the others' copy |

The TOML section is managed with the same marker machinery as the Markdown sections, using `#` comment markers, and the file is never parsed as TOML: user content outside the markers is preserved byte for byte, and no TOML dependency is added. When `[mcp_servers.lovelace]` already exists outside the Lovelace markers, appending would produce an invalid duplicate table, so the installer reports a manual step with the exact snippet instead of writing.

Per helper behaviour, all wired in `.codex/hooks.json`:

- `digest`: `SessionStart`; the helper's stdout is injected as developer context. Parity with Claude's SessionStart (Codex caps visible hook output near 2,500 tokens; the digest stays under roughly 1,500).
- `session-check`: `Stop`; exit code 2 with the prompt on stderr forces the session to continue. Parity.
- `guard`: `PreToolUse` with matcher `Edit|Write` (Codex also routes `apply_patch` through these matchers); exit code 2 blocks the call. Parity, with one caveat recorded below.
- `presence-start`: `UserPromptSubmit`. Parity.
- `presence-beat`: `PostToolUse` with no matcher. Near parity: Codex's hosted tools (for example web search) bypass tool hooks, so beats ride only on local tool calls.
- `track-active`: `PostToolUse` with matcher `mcp__lovelace__set_active_ticket` (Codex names MCP tools `mcp__server__tool`, matching the helper's expectation exactly). Parity.
- `presence-clear`: `SessionEnd` with an explicit `timeout: 3` (Codex allows SessionEnd hooks at most three seconds). Best effort: SessionEnd is advisory and also fires after thirty minutes idle; the ADR-0012 heartbeat bounds a missed clear within the presence timeout, as on OpenCode.

Codex session IDs flow into the same per-session presence and active-ticket markers as Claude and OpenCode session IDs; the helper does not care about the format.

## Consequences

- The helper stays single-sourced with zero adaptation: Codex's hook payloads carry the same field names and blocking semantics the helper already speaks. All Codex-specific knowledge lives in `codex.ts` (file locations, the TOML section, the skills format).
- Two user actions cannot be automated and are stated in the card's install hint rather than as manual steps (they are one-time Codex-side settings, not file gaps): the project must be trusted, and the Lovelace hooks must be reviewed and trusted with `/hooks`, again after any reinstall that changes the helper path. Until both are done, Codex ignores every project-level asset except `AGENTS.md` and the skills.
- Degradations, all named: presence beats miss hosted tool calls; presence-clear is advisory with a three-second budget (heartbeat-bounded); the root `AGENTS.md` pointer relies on the agent following the directive (softened by the digest arriving as injected context at every session start); and the `ticket` and `done` commands are invoked as `$ticket` / `$done` skills rather than slash commands.
- The guard caveat: Codex documents tool hooks as "a useful guardrail, not a complete enforcement boundary", and the exact `tool_input` shape `apply_patch` delivers to the matcher has not been observed in a live session; if it does not carry `file_path`, the helper's guard no-ops (fails open) for that path. Codex's permission profiles could pin `.lovelace/tickets` read-only at the OS level, but the installer does not write them: `default_permissions` is a single global setting whose ownership belongs to the user, not to an integration. Recorded as the documented hardening option.
- The root `AGENTS.md` section is shared across integrations and each install refreshes it with its own wording; the last installer's text wins, detection is marker-based on both sides, and the section always directs the agent to the same `.lovelace/AGENTS.md`.
- Codex's hooks framework is new and its schema evolves; the integration pins what it writes with tests over file shapes, and a schema change in Codex surfaces as a detection or install failure, not silent corruption.
