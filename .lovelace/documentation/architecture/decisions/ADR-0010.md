# ADR-0010: Read first, edit on intent

## Status

Accepted.

## Context

The Settings Types page rendered its whole schema in permanent edit mode: every field was a live row of wells, dropdowns, chip clusters and remove buttons, all visible at once, for a page a user touches rarely. It overwhelmed. Two redesign attempts failed before the cause was named: wrapping the editor in a raised card added boxes within boxes, and flattening the card returned to the original overwhelm. Both attempts restyled the packaging while leaving the actual problem, the number of interactive controls on screen at rest, untouched.

The app already held the answer in two places. Ticket bodies and documents render read-only and only become editable when the user presses Edit. The pattern had simply never been applied to configuration screens.

## Decision

Editor-heavy screens follow the read-first model:

- At rest, a screen is a readable summary in plain English, with zero editing controls. Each item is one quiet line: its name, a human sentence for its configuration ("list of reference to Task", "enum, from Priorities"), and quiet notes ("required", "built in").
- Editing controls materialise only when the user signals intent (clicking a row, pressing an Edit affordance), and only for the thing being edited. One open editor at a time; opening another closes the first.
- The open editor is carried by the region's one raised surface, so "this is open" is a surface that materialises, consistent with state moves, never marks.
- Creating something new ("Add field") opens its editor immediately; creation is intent.
- Built-in or locked items appear in the list as plain, non-interactive lines, described in plain English ("built in", never LOCKED).

The diagnostic rule that prevents the failed detours: when a screen overwhelms, count the interactive controls visible at rest before touching any styling. A resting screen full of live inputs is a density problem, not a surface problem; no arrangement of cards, tones or spacing fixes it. A box should mean "you can interact here" and nothing else, so if boxes outnumber likely intentions, reduce what renders at rest rather than restyling it.

## Consequences

- The Types settings page and the fields step of the init wizard follow the model; ticket bodies and documents already did. Future editors (team, statuses, any list of configurable things) adopt it rather than rendering open forms.
- One extra click is required before editing. For rarely-edited configuration this trade is correct; for high-frequency editing surfaces (quick-add, board drag) direct manipulation remains the rule.
- Component tests interact the way users do: expand a row first, then use its controls.
- Read-mode summaries carry the information a user scans for, so their wording is part of the design, not an afterthought: plain English, Title Case for human names, machine names in quiet mono.
