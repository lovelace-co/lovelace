# ADR-0014: Mapping the agent integration onto OpenCode

## Status

Accepted. Implementation is tracked as [[T-0150]].

## Context

The Claude Code integration wires a project up with four kinds of asset: the MCP server entry in `.mcp.json`, a marker-delimited section in `CLAUDE.md` that inlines `.lovelace/AGENTS.md`, two slash commands, and seven hook commands that call the `lovelace-agent` helper (`digest`, `session-check`, `guard`, `presence-start`, `presence-beat`, `track-active`, `presence-clear`). T-0150 adds the same integration for OpenCode. OpenCode's extension surface differs from Claude Code's hooks, so each behaviour needs an explicit mapping, and anything OpenCode cannot express must degrade visibly rather than silently.

Facts verified against the OpenCode documentation (v1.18 series, July 2026): project config is `opencode.json` with MCP servers under a top-level `mcp` key (`type: "local"`, a single `command` array, `environment`, `enabled`); an `instructions` array accepts file paths merged into context; `AGENTS.md` at the project root is read natively; project commands live in `.opencode/commands/*.md` with `description` frontmatter and `$ARGUMENTS`; plugins in `.opencode/plugins/*.js` run in Bun and receive typed hooks; `tool.execute.before` can block a tool call by throwing; the old config-level `experimental.hook` has been removed from the schema. There is no hook that blocks a session from finishing, no session-start context injection, and no session-end event; `session.idle`, `session.created` and `session.deleted` are observable events.

## Decision

One asset set per concern, all owned the same way as the Claude assets (marker-delimited or wholly managed files, merge-preserving JSON edits, byte-identical reinstalls):

| Claude Code asset | OpenCode equivalent |
| --- | --- |
| `mcpServers.lovelace` in `.mcp.json` | `mcp.lovelace` in `opencode.json`: `type: "local"`, the MCP server binary in the `command` array, `environment: { LOVELACE_ROOT: "." }`, `enabled: true` |
| `CLAUDE.md` section with the `@.lovelace/AGENTS.md` include | A marker-delimited section in the root `AGENTS.md` (read natively) pointing at `.lovelace/AGENTS.md`, plus `".lovelace/AGENTS.md"` appended to the `instructions` array in `opencode.json`, which is OpenCode's native equivalent of the `@` include |
| `.claude/commands/ticket.md`, `done.md` | `.opencode/commands/ticket.md`, `done.md`, same steps, `description` frontmatter, `$ARGUMENTS` |
| Seven hook commands in `.claude/settings.json` | One Lovelace-managed plugin, `.opencode/plugins/lovelace.js`, carrying the Lovelace marker; it calls the same `lovelace-agent` binary subcommands and adapts OpenCode payloads to the helper's Claude-shaped stdin, so the helper itself is not forked |
| `prepare-commit-msg` Git hook | Shared unchanged; either integration installs it, each detects the other's copy |

Inside the plugin, per helper behaviour:

- `guard`: `tool.execute.before` for the file editing tools; the plugin passes `{ tool_input: { file_path } }` to the helper and throws when the helper blocks, which stops the tool call. Full parity with Claude's PreToolUse exit 2.
- `presence-start`: `chat.message`, which fires on each user prompt. Parity.
- `presence-beat`: `tool.execute.after` for every tool. Parity.
- `track-active`: `tool.execute.after` filtered to the Lovelace `set_active_ticket` MCP tool; the plugin reconstructs the helper's expected `tool_name` and `tool_input.id`. Parity.
- `digest`: OpenCode has no session-start context injection, so the plugin runs the digest once per session and appends it to the first user message of that session via the mutable `chat.message` parts. Degraded: the digest arrives with the first prompt rather than before it.
- `session-check`: OpenCode cannot block a session from finishing. The plugin runs it at `session.idle`; when the helper reports unresolved work, the reminder is injected into the next user message instead of blocking. Degraded and recorded here deliberately: an OpenCode session can end with an unresolved ticket, and the nudge arrives one turn late. On a passing check the helper clears that session's presence, as on Claude.
- `presence-clear`: no session-end event exists. Best effort on `session.deleted`, with the ADR-0012 heartbeat making abandoned sessions go stale within the timeout anyway. Degraded but bounded.

OpenCode session IDs (`ses_` prefixed) flow into the same per-session presence and active-ticket markers as Claude session IDs; the helper does not care about the format.

The plugin spawns the helper through `node:child_process` with an absolute, forward-slash binary path embedded at install time, no shell in between, so no quoting rules apply and the same file works on Windows.

## Consequences

- The helper stays single-sourced; all agent-specific payload adaptation lives in the integration layer (the plugin template), exactly as the ticket requires.
- Three behaviours are weaker on OpenCode and say so here: digest timing, non-blocking session-check, and best-effort presence-clear. None is silently dropped; the first two remain user-visible in the session, the third is bounded by the heartbeat timeout.
- The plugin file is wholly Lovelace-owned and regenerated on reinstall; a user plugin with a different filename is never touched.
- OpenCode marks parts of its plugin surface experimental and its schema evolves; the integration pins what it writes with tests over file shapes, and a schema change in OpenCode surfaces as a detection or install failure, not silent corruption.
