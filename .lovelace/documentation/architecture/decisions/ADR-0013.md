# ADR-0013: A `lovelace` launcher on PATH, no CLI

## Status

Accepted. Implementation is tracked as [[T-0148]].

## Context

Lovelace has no standalone CLI in the MVP; the only headless surface is the agent helper the brief describes for Claude Code hooks. Even so, a user who has the desktop app installed reasonably expects to type `lovelace` in a terminal to reopen the project they were just looking at, the way VS Code's "Shell Command: Install 'code' command in PATH" works. Two constraints shape the design:

- The app has no single-instance plugin. Nothing stops a second process from starting if something on PATH execs the app binary directly, so whatever gets registered cannot simply be a symlink to it.
- Lovelace is local-first and avoids elevation anywhere in the product. A PATH registration that needed `sudo` or an OS credential prompt would be a new precedent the rest of the app does not set.

## Decision

Settings > General gets a "Command line" section with one-click install, reinstall and remove, calling three new Tauri commands (`cli_command_status`, `cli_command_install`, `cli_command_uninstall`) implemented in `apps/desktop/src-tauri/src/cli.rs`.

- **Launcher only, not the sidecars.** Only a `lovelace` entry point is registered. `lovelace-mcp`, `lovelace-agent` and `lovelace-host` stay off PATH; every integration that needs them (Claude Code's `.mcp.json`, the hooks) already references them by absolute path, so nothing downstream changes.
- **A script, not a symlink, on macOS and Linux.** The launcher is a tiny shell script (mode 0755) carrying a marker comment (`# Lovelace launcher (managed by Lovelace; do not edit)`), never a symlink to the app binary. Because there is no single-instance handling, exec'ing the binary directly would start a second app process. On macOS the script instead runs `open -b co.lovelace.desktop`, which activates the already-running instance (or starts exactly one if none is running). Linux has no equivalent activation mechanism, so its script execs the app binary's absolute path directly; a future single-instance implementation would only need to change this one line. The marker means uninstall, and the conflict check on install, can always tell a Lovelace-managed launcher apart from an unrelated `lovelace` file the user created themselves, and never touches the latter.
- **No elevation, ever.** macOS prefers `/usr/local/bin` only when it exists and is writable by the current user (probed by a real write-and-remove, since std has no portable ownership check), and falls back to `~/.local/bin` (creating it) when it is not, telling the user which directory was used. Linux always uses `~/.local/bin`. Neither path ever prompts for a password or retries with elevated privileges.
- **User-level PATH on Windows via PowerShell.** The binary is `Lovelace.exe`, so `lovelace` on PATH resolves to it case-insensitively with no separate script needed; install appends the app's install directory to the PATH stored under `[Environment]::SetEnvironmentVariable('Path', ..., 'User')`, which persists to the registry and broadcasts the environment change without elevation, since it is the per-user variable, not the machine one. Uninstall removes exactly that directory entry. Both directions are idempotent: a present entry is left alone on install, an absent one is left alone on uninstall.
- **Repair, not just install/remove.** `cli_command_status` reports whether the installed launcher's content matches what installing today would produce (`current`); a stale script, for example one left over from an old install location or an old script format, reports `current: false` and the same Install action repairs it in place. Install also cleans up a stale marked copy at the other candidate location first, so exactly one registration exists after any call, and running install twice is byte-identical and reports success both times.

## Consequences

- Running `lovelace` from a terminal opens the app, or brings the existing window to the front on macOS; it takes no flags, subcommands or arguments, and none are planned until a real CLI is in scope.
- The sidecar binaries remain reachable only by absolute path from the processes that already know them; this decision adds no new way to invoke them directly.
- macOS PATH visibility has a known GUI-app caveat: a process launched from Finder or the Dock can see a shorter PATH than an interactive shell does, since login items do not source shell rc files. The `onPath` status field can therefore read `false` immediately after a correct install; this only changes which hint copy the Command line section shows, never whether install, repair or uninstall themselves are correct.
- No new crate dependencies: the Rust side uses only `std::fs`, `std::env`, `std::os::unix::fs::PermissionsExt` and `std::process::Command` (with `CREATE_NO_WINDOW` on Windows to avoid a console flash), matching Lovelace's general preference for less machinery over more.
