# ADR-0016: Concurrency safety for multi-session projects

## Status

Accepted. Implementation is tracked as [[T-0154]].

## Context

Two or more agent sessions (or the app plus one session) work the same project routinely. Every writer used plain truncate-and-write `writeFileSync`, every mutation was an unlocked load-modify-write-reindex, and every presence beat re-resolved its ticket from the singleton `state/active_ticket`. Stress reproductions against the demo fixture confirmed four failure classes: readers observing empty files mid-write (presence ring flicker and elapsed-timer resets), a reindex reading another process's half-written ticket and persisting an index without it, a successful status move silently reverted by a concurrent update built from a pre-race read, and a session's ring lighting a ticket another session had claimed. The desktop app separately discarded watcher events arriving during its own mutations, so an agent's change landing in that window stayed invisible until the next unrelated event.

## Decision

- **Atomic writes everywhere a concurrent reader exists.** `writeFileAtomic` writes to a dot-prefixed `.tmp` file in the same directory and renames over the target, preserving the target's file mode. Used for tickets, comments, sessions, documents written by the host, state markers, presence entries, board order, graph layout, index.json and BOARD.md. Temp names never end in `.md` or `.json`, so directory scans and the presence reader never see them. Readers need no coordination: they see the old bytes or the new bytes, never a truncated file.
- **One mutation lock per project.** `withMutateLock` serialises the whole load-modify-write-reindex span of every entity mutation (create, update, delete, schema, manifest, actors, session, comment, board-order moves), using the same mkdir-as-mutex pattern as the ID counter: 25 ms retry, 5 s timeout, then a clear `MutationError`. The lock directory carries an owner token; release only removes a lock the releaser still owns, and a lock whose mtime is older than 30 s is presumed orphaned by a dead process and stolen with an atomic rename so exactly one waiter wins. Read paths, the watcher and the presence heartbeat take no lock.
- **Presence never reads the singleton.** A presence entry's ticket comes from the session's own `state/active/<session-id>` marker, else the entry's previous value, else null. The singleton `state/active_ticket` remains for the Git hook and the digest but no longer leaks another session's focus into a ring. A subagent tree still shares its parent session's single entry by design: one session, one ring.
- **The app defers its own blind spot.** Watcher events arriving during a mutation window (the mutation plus its 500 ms settle tail) are collapsed and replayed as one reload when the window closes, instead of being dropped. The replay never raises the external-change toast, since an in-window event is almost always the echo of the app's own write.

## Consequences

- Lost updates, torn reads and index drop-outs are covered by process-spawning stress tests in `packages/core/test/concurrency.spec.ts`, which import the built package and fail loudly when `dist/` is missing.
- A crash between temp write and rename can leave a dot-prefixed `.tmp` file behind; it is invisible to all readers and harmless. Nothing sweeps them today.
- A mutation legitimately holding the lock longer than 30 s (machine sleep mid-write) can have its lock stolen; the owner token keeps the release from cascading, but two writers could overlap in that window. Accepted: mutations are sub-second in practice, and the alternative is heartbeat machinery on the lock.
- Windows `renameSync` can fail transiently with `EPERM` under antivirus file holds; no retry exists yet. Revisit if reports arrive from Windows users.
- No format change: the lock directory is transient machine-local state alongside the counters' existing lock, so the spec version is unchanged.
