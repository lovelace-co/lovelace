# ADR-0011: Spec versioning, tolerance and migration

## Status

Accepted. Implementation is tracked as [[T-0094]] (foundations and error split), [[T-0095]] (tolerant reads and non-destructive writes) and [[T-0096]] (migration framework).

## Context

The spec is versioned with semver and the manifest declares the version a project conforms to, but the tooling enforces almost none of what that implies.

- The only check is in `loadManifest`: a project whose major differs from the hand-maintained `SUPPORTED_SPEC_MAJOR` constant is refused with one message. That collapses two situations needing opposite remedies: a project newer than the app (the user must update Lovelace) and a project older than the app (the tooling should migrate it).
- SPEC.md section 4 promises that minor differences are tolerated and unknown constructs produce warnings. In practice the minor is never consulted, the zod config schemas silently strip unknown keys, and `writeSchema` rebuilds `types`, `statuses` and `priorities` wholesale from that stripped parse. A construct written by newer same-major tooling is silently destroyed the next time older tooling saves the schema. The same applies to any stray key in a hand-authored file, which contradicts the no-silent-repair principle and round-trip fidelity.
- `SPEC_VERSION` and `SUPPORTED_SPEC_MAJOR` are two constants kept in sync by hand, compiled into four consumers (core, host, MCP server, agent helper) that can drift across rebuilds.
- No migration machinery exists. The 2.x to 3.0 break was migrated by hand in this repository; an outside user's 2.x project would be refused with no pathway.

## Decision

### Each semver part has one operational meaning

- **Major**: the file format changed shape. Older tooling cannot operate safely; crossing the boundary requires a migration.
- **Minor**: additive constructs only. Older same-major tooling must still read the project and must never destroy what it does not recognise. If a proposed minor change would require rewriting existing files, that is the definition of it being major.
- **Patch**: prose clarification in SPEC.md. No format change, no code impact.

This is what makes versioning scale: each major costs one migration step, and minors cost no per-version code at all, because tolerance is generic rather than version-specific.

### One decision point

A single version module in `packages/core` holds `SPEC_VERSION` as the only source; the supported major is derived from it, never declared separately. One classification helper compares a project's declared version against the tooling and every consumer routes through it:

| Project vs tooling | Behaviour |
|---|---|
| Project major above tooling | Refuse: the project needs a newer Lovelace |
| Project major below tooling | Refuse to operate as-is: offer the migration flow |
| Same major, any minor or patch | Open normally |

`ConfigError` carries a machine code (`spec-too-new` or `spec-needs-migration`) plus both versions. The host serialises the code and the app switches on it rather than pattern-matching message strings: `spec-too-new` renders a dedicated screen naming both versions and pointing at the app update; `spec-needs-migration` opens the migration flow. The MCP server and agent helper report the same classification textually and direct agents to open the project in the app; headless surfaces never rewrite a project on their own.

The warning for newer-minor projects is driven by evidence, not arithmetic: validation warns when unknown constructs are actually present in the files, so a project stamped with a newer minor that uses no newer construct opens silently.

### The declared version is a floor

Because minors are additive, a valid 3.0 project is also a valid 3.1 project. Tooling therefore never bumps `spec_version` opportunistically; only a migration rewrites it. This keeps diffs quiet in teams running mixed app versions and keeps the declaration honest as a minimum, not a claim about which constructs are present.

### Tolerant reads, non-destructive writes

Config parsing passes unknown keys through instead of stripping them, and validation reports each as a warning (`schema/unknown-key`, naming the file and key), never an error. Mutations patch the keys they know per node and leave unrecognised keys in place, the way `writeManifest` already patches the document in place. An older app editing a newer-minor project must round-trip the newer constructs untouched.

### Migration framework

A registry in `packages/core` holds one step per major boundary:

- Each step declares the major it upgrades from and to, a plain-English summary shown to the user, a `plan` (dry run listing which files change and how) and an `apply`.
- Steps chain, so a project several majors behind migrates stepwise, each step small and testable in isolation.
- Steps patch YAML documents the same way the mutation layer does, so migrated files keep comments and produce minimal diffs.
- After apply the framework stamps `spec_version`, reloads, runs full validation and reindexes. A post-migration validation failure is reported, never silently repaired.
- Git is the safety net, not bespoke backup machinery: `.lovelace` lives in the user's repository by design, and the confirm screen instructs the user to commit before migrating.
- The migration floor is 2.x. The framework ships with the 2.x to 3.0 step as the reference implementation; anything older is refused with an honest message that the format predates supported migrations.

In the app, an older project opens to a dedicated screen (not a toast) listing each pending step's summary, the commit-first note, and one primary action; on success the project reloads normally.

## Consequences

- Every future breaking change adds exactly one migration step with fixtures; every additive change adds nothing to version handling. The SPEC.md changelog remains the human record and the migration registry becomes the machine record of breaking changes.
- SPEC.md section 4 is rewritten to state these semantics and the new tooling obligation to preserve unknown keys on write. That obligation is additive, so the rewrite is a 3.1.0 bump.
- The unknown-key preservation work also fixes a live round-trip bug for hand-authored files, adjacent to [[T-0079]].
- Each migration step is tested with a fixture project in the old format, a snapshot of the migrated output, an assertion that the result passes current validation, and an idempotence check.
- Version classification lives in one module, so a stale sidecar disagrees with the app in one visible place instead of four independent constants.
